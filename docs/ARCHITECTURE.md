# 架构与决策记录

> 这份文档记的是**为什么这么设计**，不是怎么调用。调用看 README。
> 每个决策后面都跟一句「不这么做会怎样」——那是它存在的理由。

---

## 一、数据流

```
用户链接
   │
   ├─[1 抓取] extract.fetch
   │     微信 → 转义还原 + js_content + 块级标签换行 + data-formula 还原
   │     arXiv → abs 页取作者序/日期/摘要，html 页取全文（失败则用摘要）
   │     通用 → 剥脚本样式，优先 <article>
   │     全失败 → 用户粘贴正文（pasted 模式，作者序标「未核」）
   │
   ├─[2 定性] LLM  → {genre, author_note, claims[]}
   │     产出「可核项清单」，不是摘要
   │
   ├─[3 核验] LLM  → {items:[{verdict, evidence, fix}]}
   │     verdict ∈ {确证, 不实, 半对, 未核}
   │
   ├─[4 实算] LLM 给表达式 → safe_eval 执行 → 记录 value/status
   │     成功 = 已实算；被拒或算不出 = 未实算（带原因）
   │
   └─[5 成稿] 模板拼装 + LLM 评述（禁数字）
         数字全部由模板从第 4 步记录注入
         评述若含数字 → 报告自动加「未经实算」提示
```

前四步是「取证」，第五步只是排版。**证据先于文字**，这是整个设计的骨架。

## 二、三个不可退让的决策

### 决策 1：数字不过模型的手

报告里的每个数字，都由 `render_report()` 从 `calc["items"]` 直接格式化写入。LLM 只写不含量值的评述段落，且若它违规写了数字，模板会自动插入一行提示。

**不这么做会怎样**：模型会在复述时把 `0.0068` 写成 `0.68`、把 `差 0.6 个百分点` 模糊成 `差 6%`。刚算准的数被它改一手，前面四步全白做。这是最隐蔽也最致命的一类错误——报告看起来完全正常。

### 决策 2：不执行模型生成的任意 Python

`server/safe_eval.py` 用 AST 白名单：只允许 `+ - * / ** %`、一元正负、以及 `sqrt/log/exp/abs/min/max/round/sin/cos` 等；拒绝 `Attribute`/`Subscript`/`Lambda`/`Comprehension`/`JoinedStr`/`NamedExpr`；幂指数绝对值 ≤ 64；节点数 ≤ 120；结果须为有限实数。

**不这么做会怎样**：这是把一个「能执行任意代码的接口」暴露在公网上，而且执行的内容由可以被提示注入的模型生成。`__import__('os').system(...)` 只需要一次成功。

代价是算不了线性代数。判断：读解的算据九成是**四则运算与百分比**，白名单够用；剩下的一成走沙箱（见 §4），不该为了它们牺牲整条链的安全。

### 决策 3：降级必须显式

转录相关两节的分工（v2.3）：`转录校对` 是事实清单（改了哪些、风险多大），`需要回听的地方` 是行动建议（只筛高风险项与未采纳的存疑项）。
筛选用 `_fix_risk()`：类别看后果（数字/专名/断句/同音字/补字/删字/改写），建议看托底（`规则替换`、`上下文`、`不通`、`标准译名` 等视为硬依据）。
两节都不空则不出第二节——空节的缺席本身传达「无高风险项」，不再补兜底话。

三种状态各有明确文案：`已实算` / `未实算（原因）` / `未核（原因）`。抓取失败不返回半成品，未配 key 不返回假报告。

**不这么做会怎样**：用户分不清「这篇没问题」和「这篇没查」。前者是结论，后者是空白，混在一起就等于把空白当结论卖。

### 决策 4：能算不等于在验证（2026-11-16 补）

第一版把「模型给出算式 + 求值成功」当成实算。实测被打脸：一篇芯片科普的报告里，
四条所谓实算全是 `3/4`、`50000`、`600/100`、`0.1` —— 纯常量表达式，把原文数字换个写法再写一遍。

于是加了三条判定：

| 条件 | 缺了会怎样 |
|---|---|
| 表达式必须含变量（`has_variable`） | 否则是复述原文 |
| 必须给出原文的声称值 `expected` | 否则算出来也无从判对错 |
| 实算与声称相差 ≤ 1% 才算「已实算」 | 否则没人在比 |

五档状态：`已实算` / `不符` / `待比对` / `仅供参考` / `未实算`。**只有前两档构成验证**，
`待比对` 是「算得出但声称值是中文表述、无法自动解析」，把两个数并排给人看，不冒充已验证；
报告里若全部落在后两档，末尾会显式加一句「本轮没有形成可判定的实算」。

同一批修复还处理了「空条目」：模型会给一堆 `{}` 占位，旧代码只判列表非空，
于是渲染出六行空表格。空表比不出现更糟——读者会以为内容丢了。现在按内容过滤，
过滤后为空则整节不渲染。

### 决策 5：溯源只补「未核」，且低质量证据不许升级

接 Search 之前，报告里那 7 个「未核」是死结：没有出处就不许下结论，于是整篇报告只剩「查不到」。
接上之后可以自动补，但必须守住三条：

| 约束 | 理由 |
|---|---|
| 只对 `verdict == "未核"` 的条目检索 | 已能判定的再查一遍纯属烧钱；`SEARCH_MAX_ITEMS` 默认 3 |
| 只有 `authority ≥ 3` 或 `rerank_score ≥ 1.5` 的结果能单独支撑「确证」 | 否则一篇转载博客就能把「模型觉得」洗成「已核」 |
| 检索失败/无结果 → 保持「未核」，并在报告里写「未溯源」 | 与「不降级为假报告」同一条原则 |

判定被更新时，核验表多一列「出处」，只写域名不写全文链接——读者要的是「这说法有没有正经来源」，
不是「点进去看」。低质量结果单独标 `[仅供参考]`，不参与判定。

**权威判定必须域名优先，不能分数优先**：搜索接口的 `authority` 分衡量「相关性/质量」，
不衡量「来源是否一手」。实测 `mp.weixin.qq.com` 拿到 authority=3，公众号就被当成权威源去
支撑「确证」。所以 `quality()` 先查域名：命中二手平台（公众号、门户、头条、知乎、百科、
快科技等）一律 `relevant`，分数再高也不动摇；命中一手来源（acm.org、asml.com、zeiss.com、
.gov、.edu 等）则 `authoritative`，分数再低也认；都不命中才看分数。

一个刻意的限制：**不用 `need_content: true`**。它会把整页正文拉回来，token 成本翻几倍，
而判定只需要 `summary`（600–800 字，本来就是给模型读的）。要全文时用 `/tools/fetch`。

### 决策 6：二次检索只在前一批「全非权威」时触发

实测暴露了一个尴尬结果：「英伟达没有晶圆厂」被判「确证」，而出处写的是「微信公众平台、新浪财经」。
形式上满足了「有结果支持」，实质是给自媒体背书。

两级补救：

1. **证据分三级**，只有 `authority ≥ 3` 才能判「确证」（见决策 5）；
2. **若第一轮一条权威源都没命中**，按官方域名补检一次（`site:xxx.com`）。

域名从哪来：一次额外调用让模型给候选（厂商官网 / 监管机构 / 标准组织 / 一手财报），
再用黑名单兜底过滤——公众号、门户、百科、问答站、资讯站一律不接受。
**宁可查不到，也不许拿资讯站凑数。**

成本：共用 1 次域名候选调用，每项最多 +2 次检索；只在「全非权威」时才触发，命中过权威源的不再补检。

## 三、失败模式清单

| 失败 | 现状处理 | 还可改进 |
|---|---|---|
| 微信公众号反爬 / 空壳页 | 报错 + 提示用粘贴入口 | 换 UA 池、cookie 池 |
| arXiv 全文页断流 | `_get` 重试 2 次，失败退到摘要 | 缓存已抓正文，避免重复拉 110KB |
| arXiv 整站不可达 | 报错 | 加 ar5iv / 镜像源降级 |
| 模型返回非法 JSON | `chat_json` 做 ```json 剥壳 + 大括号兜底 | 二次修复调用 |
| 模型给不出表达式 | 该条标「未实算」 | 提示词加少样本示例 |
| 模型评述里夹数字 | 报告自动加「未经实算」提示 | 生成后剥离数字并回填占位符 |
| 单次读解超时（客户端断开） | `BrokenPipeError` 直接收尾 | 转异步任务 + 轮询 |
| 并发打满 | `ThreadingHTTPServer` 无限线程 | 换 gunicorn/uvicorn 或信号量限并发 |

最后两行是**上线前必须改的**：线程无上限 + 长任务 = 一次流量高峰拖垮整机。

第一行已在 v2.9 处理：`Semaphore(MAX_CONCURRENT=8)` 卡住「同时在跑的任务数」，等不到额度直接 503 并断开连接，不做无上限排队（让空线程卡在信号量上只是把线程数问题换个地方堆着）。用 `BoundedSemaphore` 是为了让漏配对的分支当场抛错，而不是把额度悄悄多还一次。
剩下的「换多进程服务器」仍未做 —— 单进程 + 信号量只能挡住「并发任务」，挡不住「并发连接」本身。

## 四、需要 numpy 的那一成，怎么处理

两条路，按是否愿意接受「执行模型生成的脚本」来选。

**路线 A（推荐）**：扩白名单。给 `safe_eval` 加一组**固定的核验原语**（`det2`、`trace`、`frobenius_norm`、`pow_sum` 等），模型只能填参数，不能写代码。安全边界不变，覆盖面扩大。

**路线 B**：真沙箱。Docker 容器 + 无网络 + 只读根文件系统 + `--memory=256m --cpus=0.5` + 10s 超时 + 输出上限。适合真需要 `numpy.linalg` 的场景。

**不要选**：在服务进程内 `exec()` 模型给的代码，指望靠正则过滤 `import`。那只是延迟出事。

## 五、成本

单次读解固定 4 次模型调用（定性 / 核验 / 实算 / 评述），正文截断到 24000 字。

粗估（按 deepseek-chat 量级）：输入约 1.2 万–2 万 token（四次累计，正文重复送入），输出约 3–4 千 token。**主要成本在「把正文重复送四遍」**。

降本三步，按性价比排序：

1. **同一篇缓存**（URL + 正文哈希为键，24h）。重复请求几乎为零成本。
2. **合并 2、3 步**：定性与核验可以一次调用完成（省一遍全文），代价是核验深度略降。
3. 长文只送摘要 + 命中数字的段落（需先做定位，工程量最大）。

## 六、扩展路线

| 阶段 | 内容 | 前置条件 |
|---|---|---|
| M1（当前） | 三源抓取、五阶段、白名单实算、单页前端 | 无 |
| M2 | 任务队列 + 结果持久化（可分享的读解链接） | 一台有 Redis 的机器 |
| M3 | 核验原语扩充（行列式、特征值、幂和） | 无（不引入沙箱） |
| M4 | 多文档对比（同一事件两家报道的交叉核验） | 抓取层稳定 |
| M5 | 把「可核项」变成社区可提交的标注集，形成回归测试 | 有真实用户量之后 |

M4 才是这个项目真正有意思的地方：**单篇核验只能发现内部矛盾，跨源核验才能发现外部错误**。但它依赖 M1 的抓取稳定到可以信任。

## 七、视频号：把「二手」做成结构字段

视频号路径的工程难点不在抓取（微信 UA 下服务端直出），在**层级**。

三件事必须由代码保证，不能指望提示词自觉：

1. `doc["layer"]` 是**结构字段**，不是文案。抓取层写死「L1 二手：元宝对视频的总结」，报告无条件渲染这一行 —— 它不依赖模型是否记得提。
2. **覆盖率由模板算**。时长 × 4–5 字/秒得口播字数区间，再与总结字数相除。理由同决策 1：凡数字，不经模型之手。
3. 视频额外字段（`who_speaks` / `transcript_risks` / `title_claims`）在 triage 的 schema 里**固定存在**，非视频时返回空数组。这样渲染代码只有一份，不会因为漏字段崩。

一个反例说明第 1 条为什么不能省：

示例视频里，元宝把《素问》的「七损八益」写成了「七胜八益」。若报告不声明「这是元宝的总结」，读者会认定「这段视频讲错了」。实际有两种可能：元宝听错了，或者视频真讲错了 —— **两者的处置完全不同**（前者换工具，后者换信源）。分层标注的唯一作用，就是让读者有能力做这个区分。

同理，`answerTime` 是元宝整理答案的日期，**不是视频发布时间**。字段名与报告标签都必须写清，否则时效判断会出错。

## 九、ASR：把 L1 升成 L0，以及为什么值得为它做切片

一个在实现前必须确认的事实：**元宝分享页没有媒体直链**。`coverUrl` 指向 `finder.video.qq.com/stodownload?...`，看着像播放地址，实际是封面图。所以原声只能由用户提供（微信「保存视频」→ 上传）。

这条约束决定了架构：ASR 不接在「抓取」后面，接在「上传」后面。

**三个工程点，都不是可选项：**

1. **先抽音轨再送转录。** 用户传一个 200MB 的 mp4，直传会撞上大多数接口的体积上限。用 `ffmpeg -vn -ac 1 -ar 16000 -b:a 32k` 抽出 mp3，5 分钟约 2.4MB —— 体积降两个数量级，音质对 ASR 完全够。这一步不做，长视频基本必然失败。
2. **超长要切、切了要合。** 20 分钟切一片，转录后按 `seg_sec` 累加偏移。偏移不入库，时间戳就全错，而时间戳错了，报告里的证据片段就定位不到原声。
3. **ASR_PROMPT 优先级高于换模型。** 口播错字集中在专名：古籍、人名、流派、术语。给一段术语提示（`黄帝内经，素问，七损八益…`），比从小模型换到大模型更能降错字率，且成本为零。

**升到 L0 之后多出来的一节，才是做 ASR 的真正收益。**

在此之前，报告只能核「总结是否自相矛盾」；有了原声，才能核「总结是否忠实于原话」。后者是外部校验，前者只是内部一致性——两者价值差一个量级。

这一节由 triage 顺手完成（不额外调用，省一轮成本），四类走形：条件句说成断言、某人观点说成经典原文、数字量级对不上、否定说成肯定。

**风险清单：**

| 风险 | 处置 |
|---|---|
| 音频上传第三方泄露内容 | 文档明示；涉密场景用 `ASR_BACKEND=local` |
| ASR 错字被当成原文 | 报告头尾都标「ASR 可能有错字，引用前回原声核」 |
| 单次转录耗时数分钟，HTTP 连接被断 | 已用 SSE 保活；生产建议转异步任务队列 |
| 上传占盘 | 分析结束即删；被中断时留残件，建议加定时清理 |
| 300MB 上限被滥用 | 与限流共用配额；公开部署请按实际调低 |

## 十、如果要贡献

优先接受这三类改动：

1. **新的攻击用例**（`test_safe_eval.py`）——任何能绕过的写法都是高价值报告。
2. **新的抓取源**（有明确结构、有公开页面）。
3. **报告模板的可读性改进**（但不得引入「看起来像结论的模糊表述」）。

不接受：为了「说得更全面」而放宽「未核 / 未实算」的标注要求。
